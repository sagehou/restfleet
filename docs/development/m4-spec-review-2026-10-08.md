审阅基线：已合并 `main`，`07a85e39169c416817df97ecb5cd63224ebb9d8a`（#60）。本报告是源码与文档审阅结果及调整建议，不修改规范、ADR、里程碑退出条件或安全验收，不构成新架构批准。审阅期间只执行只读检查与文档编辑，没有本地编译、测试、认证或服务启动。

后续整理（2026-10-14）：实施计划已将 M4 批次历史单列、明确剩余完整流程，并把依赖真实执行器的 AGT-005/006 集成归到 M6；原验收要求与发布门禁保留。部署 §7.10 的“续期”已按 ADR-0019 区分授权续期与占用延长。用户随后明确：离线窗口可配置、默认 72h；Gateway 离线暂停备份并报错，保留配对；不扩展离线冷启动恢复，rclone 在部署后的 Actions 验证。该决定以 ADR-0032 及 schema 16 落实。以下正文保留审阅时的历史问题和建议；旧 12h/24h 数值及“取舍待决定”不再代表当前合同。生产会话与完整停止协调仍待交付，不因文档整理宣称完成。

## 结论

M4 长期未退出有两类原因：规格没有闭合关键依赖和运行协议；实施持续按安全组件拆批，却迟迟没有交付真实 Agent 可用的完整链路。不能把进度慢全部归因于安全要求，也不能把内部组件测试通过当作产品完成。

原始计划（`458631a:IMPLEMENTATION_PLAN.md`）的 M4 是 OneDrive、per-Host Repository、Gateway、凭据轮换与 REP-001–012。当前计划增加三后端、独立 Gateway 离线授权、加密回写与隔离启动等，退出测试扩到 REP-001–060，并记录三十批工作。“三十批”不是三十个独立 PR，部分批次合在 #51 中。扩展中的安全措施各有理由，但计划没有同步重建依赖与明确的产品交付边界。

当前判断：M4 基础组件已有大量实现，M4 产品交付仍未完成；尚不能部署为完整备份系统。

## 1. 离线时长要求没有一致的可验收定义

证据：

- [AGT-005](../spec/12-acceptance-tests.md#4-agent-连接与配置) 要求控制 API/DB 离线 12h、Gateway 在线时，Agent 按本地计划成功备份。
- [安全模型 §8.3](../spec/02-security-model.md#83-gateway-有界离线授权已接受生产接线待完成) 要求授权不晚于中心签发后 12h 仍可使用，撤销/禁用最多延迟 12h。
- [ADR-0017](../adr/0017-bounded-offline-gateway-authority.md) 已明确承认：这不证明任意失联时刻之后仍有完整 12h；不得缩短实验或从接收时重新计时。

若将 AGT-005 解释为任意时刻断线后完整可用 12h，两项要求无法同时保证。例如 00:00 签发、01:00 失联，授权最多到 12:00，断线后只剩 11h；如果计划任务在 12:30 触发，就必须拒绝。定期续期只能缩小差额，不能消除断线发生在续期前的边界。

实际剩余窗口还受原占用期限限制：

```text
可用截止 = min(最后有效授权截止, 原备份占用截止)
断线后剩余窗口 = max(0, 可用截止 - 断线时刻)
```

这是可用性承诺与安全上限的取舍，不能靠继续增加实现批次解决。建议保留已接受的签发后 12h 安全上限，将可用性明确为剩余授权窗口，并在状态中显示截止时间；这会改变 AGT-005 的完整离线承诺，必须经过明确决定和同批规范修订。若必须保证健康在线状态下任意断线后完整 12h，则需同时定义续期间隔、最大交付延迟与时钟余量，并重新批准更大的授权寿命/撤销延迟上限；占用期限也必须满足该保证。

当前 AGT-005 仍未完成。本报告没有选择或应用上述取舍。

## 2. 里程碑退出顺序存在前置依赖错误

证据：

- [计划 M5](../../IMPLEMENTATION_PLAN.md#m5--templates-plans-and-local-scheduler) 的退出包含 AGT-003–006 和中心离线 12h 调度测试；AGT-005 要成功备份，AGT-006 要补报离线产生的 Operation。
- [计划 M6](../../IMPLEMENTATION_PLAN.md#m6--backup-execution) 才实现 Agent Restic 执行、结果缓冲和本地结果 reconciliation。
- [ADR-0014](../adr/0014-gateway-owned-lock-cleanup.md) 要求会话绑定可信 Operation，并禁止把每次定时备份改成必须在线请求 Control API。
- [部署 §7.10](../spec/09-deployment.md#710-有界离线授权与待回写目标) 把会话交付、恢复和相关离线验收继续放在 M4 内；这些组件必须提前明确如何接入 M5/M6，但提前定义接口不等于交付完整调度与备份。

在“一次一个里程碑且前一里程碑全退出才进入下一里程碑”的执行方式下，M5 必须证明 M6 尚未实现的行为。这个错误在原始计划中已经存在。它也推动实施不断向 M4 填入后续链路的前置组件。

建议保留一个里程碑一次的纪律，但让退出条件遵循真实依赖：M5 验收配置接受和本地调度的持久化、去重、时区与故障行为；真实备份、离线 Operation 补报与 AGT-005 放在 M6 集成验收，仍是 V1 发布硬门禁。M5 的调度测试不能据此宣称真实备份成功。

REP-016 的真实云备份、索引和恢复可以用固定引擎的安全集成程序验收，并不必然等待完整 M8/M9 用户界面。应明确它验收的是后端还是产品流程，不能笼统把所有跨模块测试视为依赖冲突。

## 3. 长期身份与单次会话能力之间缺少生产协议

证据：

- [安全模型 §7](../spec/02-security-model.md#7-repository-凭据) 和 [Agent 协议 §13](../spec/04-agent-protocol.md#13-credential-revision) 定义 per-Host 长期 gateway password、下发/ACK 和默认 15 分钟轮换 overlap。
- [ADR-0014](../adr/0014-gateway-owned-lock-cleanup.md) 要求每次会话独立随机能力；长期密码不能证明锁归属。
- [ADR-0031](../adr/0031-gateway-service-lifecycle.md) 明确当前 session password 与 Agent 长期密码不同，生产申请/交付尚未连接。
- `internal/gateway/supervisor_linux.go:229–258` 创建单次能力，只通过可信进程内 callback 借出；`internal/gateway/service_linux.go:252` 仍以 `WithBackup` 接缝提供入口。
- `api/proto/restfleet/agent/v1/agent_control.proto:13–39` 目前只实现连接、配置、凭据与确认等消息，没有备份会话申请/交付消息；`cmd/restfleet-gateway/main.go:22–36` 只有版本、来源初始化/导出和回放命令。

因此，Agent 已保存仓库凭据不等于能访问当前 Gateway 数据面。这个缺口不应靠让长期密码拥有任意锁删除权来填补。

建议在下一批实现前先补齐一个端到端协议：长期身份如何验证并限制到本 Host；如何从已批准的授权/占用获得单次会话；离线时如何创建和验证本地 Operation 的绑定；能力如何受保护交付、去重、过期、取消与清理；两种密码的轮换如何影响既有会话。离线启动不能再依赖不可达的 Control API，也不能只信任 Agent 自报的 Operation。

[V2 范围中的“可选短期 gateway credential”](../spec/11-v1-scope.md#5-v2) 也需要澄清与 V1 内部会话能力的区别。这是术语和协议边界不明确，并不自动证明 ADR-0014 越过了 V1 范围。

## 4. 有保守停止规则，缺长期运行与恢复闭环

证据：

- [ADR-0016](../adr/0016-durable-backup-admission-fences.md) 限制占用最多 24h，到期禁止使用但保留 fence；释放要求可信 owner 证明完整清理。
- [ADR-0019](../adr/0019-durable-gateway-decisions.md) 保持占用期限不可变，授权续期不能超过原占用截止。
- [部署 §7.10 第 1 项](../spec/09-deployment.md#710-有界离线授权与待回写目标) 却仍描述续期需要 schema 11 期限迁移。它与后来选择的“原期限内续期”没有统一，应明确区分授权续期与占用延长。
- [安全模型 §8.4](../spec/02-security-model.md#84-gateway-单次初始化材料) 禁止已提交初始化意图重发；[§8.7](../spec/02-security-model.md#87-gateway-单次启动生命周期) 要求任一 owner 永久失效停止整次运行，Close 不封存、不释放。
- `internal/persistence/postgres/backup_admissions.go:234–272` 有中央释放事务，但调用方必须另行证明清理；`internal/server/gateway_startup_linux.go:80–84` 明确初始化函数不负责续期、封存、释放或恢复。现有显式 `replay` 也只回放记录。

这些拒绝规则保护了维护互斥和旧会话隔离，不能直接删除。缺口在于没有定义并交付“谁持久负责 owner、如何证明退出、如何封存回写、如何安全释放并建立下一次运行”的正向流程。若无新协议，持续在线的服务也会受最长 24h 占用限制；写一个 `run` 命令不能解决这个问题。

建议先确定运行周期与恢复状态机：初始化、可用、排空、已停止待确认、已封存、已释放、可建立新运行；每次转换明确可信证据与故障重试规则。正常清理后释放再建新运行、原 fence 连续延长，是不同方案，必须明确选择并同步规范；不得通过自动过期释放或无证据接管实现“恢复”。首次启动的公网就绪条件与运行中的控制面不可达、剩余授权、队列容量、恢复阻塞状态也应分别定义。

## 5. 计划和规范混入批次历史，导致判断失真

`IMPLEMENTATION_PLAN.md` 的 M4 同时记录三十批历史和未来计划；`docs/spec/09-deployment.md` §7.3–7.23 按实现批次累加，早期“尚未接入”与后期已有组件并存，读者必须自行推断哪些描述仍有效。

`docs/development/m4-gateway-pr-review.md:3` 仍写 #51 未合并；`docs/development/progress-assessment-2026-10-03.md:13,18` 仍把来源装载作为待合并分支并描述旧 command 状态。这些应作为带明确基线的历史记录，不能继续代表当前进度。

建议当前计划只保留完成能力、剩余交付、依赖和退出证据；批次记录移到交付历史。规范保留当前合同和限制，清除已被后续决策取代的阶段性说法。新增安全负向测试应继续保留，但不应每加一个内部测试编号就扩大产品里程碑范围。三种真实后端的人工证据必须单列状态、环境条件与责任，缺失仍阻止相应门禁通过。

## 建议的收敛路线

以下是待采用的路线，不改变当前 M4 未完成状态：

| 顺序 | 交付 | 验收与边界 |
|---|---|---|
| 先修正文档 | 明确离线时间取舍、会话/Operation 合同、运行与恢复状态机；重排 M5/M6 验收归属 | 涉及安全、API、持久化或协议变化的决定同步 ADR；退出测试不能静默删除 |
| M4 收敛 | 串接现有 Service，交付生产会话入口、daemon/readiness、可信停止/回放/封存/释放与新运行、rotation/READY | Actions 经真实入口和生产配置完成客户端备份读回、轮换、停止及重启恢复；客户端夹具不冒充产品 Agent；保留真实三后端门禁 |
| M5 | Template/Plan 和 Agent 本地 scheduler | 配置/调度持久化、去重、时区、misfire、last-known-good；真实备份集成不在此提前宣称完成 |
| M6 | 真正 Agent 执行 Restic、Operation/result reconciliation | 从计划或手动触发到 Gateway、快照和结果的完整链路；在已决定的时长合同下验收 AGT-005，保留 V1 发布门禁 |

下一批应围绕一段可验收的用户流程组织改动，例如“已登记 Host 获得会话，客户端备份并正确结束”，复用现有安全组件。除非该流程确实暴露新的边界缺口，不再默认单独添加一层内部原语、一个 ADR 和一组测试后继续留下整条生产链路。

规格修订之前暂停新功能实施是合理的；修订后应按上述收敛交付推进，不把“进入下一 milestone”本身当作目标，也不以降低隔离、审计、fencing 或验收换取完成标记。
